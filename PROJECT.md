# Yaniv Scorekeeper

A fast, offline scorekeeping app for live games of Yaniv — the Israeli card game. Replaces the paper scoresheet; does not simulate the game.

## Business Purpose

Yaniv is played with physical cards, but the scoring is fiddly to track by hand: detecting an **Assaf** (a failed Yaniv call), applying the **+30 penalty**, handling the **exact-100 score-halving** house rule, and keeping cumulative totals straight across an open-ended number of rounds. This app does that math automatically so players can focus on the game. It does **not** deal, hold, or simulate cards — the cards stay on the table.

## Target Users

Casual Yaniv players — the game is popular among Israeli backpackers, soldiers, and students. One person ("the scorekeeper") holds a phone at the table and records each round. Typical conditions: a single device, often **no internet** (hostels, bases, buses). Speed and offline reliability matter more than features.

## Features

**v1 scope (agreed 2026-06-02):**

- **Game setup** — add 2 to 6+ players by name (no hard cap at 5); choose Yaniv threshold (7 default, or 5 / 11); toggle the 100-halving house rule; optionally set an elimination/knockout score.
- **Round entry** — tap who called "Yaniv!", then enter each player's revealed hand total. The app resolves the round (see Scoring Engine) and updates cumulative scores.
- **Mid-game join** — a player can join a game already in progress. They start seeded at the **highest cumulative score among the still-active (non-eliminated) players** at the moment they join, so a latecomer gets no unfair head start. They take the next seat — the seating circle grows. (See Scoring Engine for the precise seeding rules.)
- **Automatic scoring** — successful Yaniv vs. Assaf detection, +30 penalty, hand-value scoring for everyone else, and the exact-100 halving rule (any positive multiple of 100 — 100, 200, 300, 400, … with no upper limit) applied with a visible callout.
- **Live standings** — running cumulative scores shown in **static seating order matching the physical table** (the order players sit around it), **never reordered by score**. The leader is only *indicated* — a crown/highlight — never repositioned to the top. A clear indicator shows who starts the next round.
- **Round history — the vertical scoresheet** — the Big Board view is a full scoresheet grid, the digital twin of the handwritten paper sheet: players as columns (static seating order), rounds as rows down the page (oldest at top), each cell the running cumulative total after that round, a left round column noting who called and whether it was a Yaniv or an Assaf, and in-cell markers for the special moments (Assaf +30, 100-halving, elimination, mid-game join). The scoresheet IS the round-by-round history.
- **Undo / edit last round** — mis-entered totals are common; the scorekeeper can correct the most recent round and have everything recompute.
- **Elimination & game end** — open-ended play; optional knockout threshold removes a player who crosses it; "end game" crowns the lowest cumulative score as winner at any time.
- **End-of-game stats** — the final screen shows each player's count of successful "Yaniv!" calls during the game (a per-game stat, computed from this game's round history — no cross-game database needed).
- **Online landing page** — the public URL the app is shared by. Before installing, a visitor sees what the app is, why to install it (works offline, full-screen, no app store), **step-by-step install instructions for both Android and iPhone/iPad**, and **both** guides: **How to Use** (operating the app) and **How to Play** (the rules of Yaniv). This page is how every device gets its own copy (see Distribution model).
- **In-app Help screen** — reachable any time from inside the installed app via a **"?" / Help** control on the Play and Setup screens. It carries **two clearly-separated, independently-titled bodies — "How to Use" (how to operate the scorekeeper) and "How to Play" (the rules of the game, drawn from the Yaniv rules)** — on two labelled tabs/sections, plus a "share this app" link. It omits the install steps (you're already installed). Both bodies are authored **once** and shared between the landing page and the in-app screen so they can never drift apart. (Drafted copy: `docs/landing-and-help-content.md`, Section A = How to Use, Section B = How to Play.)

## Scoring Engine (the core logic)

For a round where the caller's hand value is `C` and the lowest *other* player's hand value is `L`:

1. **Successful Yaniv** — `C < L` (caller is strictly lower than *every* other player):
   - Caller scores **0**.
   - Every other player scores their own hand value.
   - Caller starts the next round.
2. **Assaf** — `C >= L` (any other player ties or beats the caller):
   - Caller scores **`C + 30`**.
   - Every other player (including the catcher) scores their own hand value.
   - The catcher starts the next round.
3. **Cumulative update + 100-halving** — add each player's round score to their cumulative total, then for any player **whose total the round actually MOVED** and whose new total is **exactly** a positive multiple of 100 (100, 200, 300, 400, … — no upper limit), halve it and show a callout (e.g. "Dana hit 100 → halved to 50"). **A player who scores 0 has not landed on anything and is never halved** — see "Halving — no cascade" below.
4. **Elimination check** (if a knockout score is set) — any player whose cumulative total crosses the threshold is marked out.

**Edge-case rule (default, overridable as a house rule later):** if an Assaf has multiple catchers (several players tie or beat the caller), the **lowest hand among the catchers** starts the next round; ties broken by seating order after the caller.

**Mid-game join — seeding rules:**

1. **Seed score** — a joiner starts at the **highest cumulative score among the still-active (non-eliminated) players** at the moment of joining. This prevents a latecomer gaining an unfair head start over the field.
2. **No halving on the seed** — the seeded starting score does **not** trigger the 100-halving rule, even if the seed is itself an exact multiple of 100. Halving applies only to scores produced by playing rounds, not to the entry seed.
3. **Normal play thereafter** — from the join onward the player is treated like any other. Future round scores that land their cumulative total on an exact multiple of 100 **do** halve as usual.
4. **Never instantly eliminated** — a joiner is never knocked out at the moment of joining, even if their seed equals or sits at/below an elimination threshold that a struggling player is already near. They enter the game in play.
5. **Replayable & derived** — the join is recorded as an event in the round history, so undo/edit and recompute-from-history continue to hold. The seed is **derived at recompute time** from the active players' totals as of the join event — it is **never stored** — so editing earlier rounds keeps the seed correct.

## UX Considerations

- **Mobile-first** — designed for one phone held at a table; large tap targets, minimal typing, fast round entry.
- **Offline-first** — fully usable with no connection; installable to the home screen (PWA).
- **Crash-safe** — game state persists to local storage on every change, so an accidental refresh or app-close never loses the game.
- **Legible at a glance** — standings and "who's next" readable across the table; clear, celebratory callouts for Assaf and 100-halving moments.
- Accessibility: high contrast, readable font sizes, works one-handed.

### UI Design Direction (approved 2026-06-02)

Yaniv **deliberately diverges** from Roger's executive house style. It is a casual party/card game, so the UI takes on a fun, gamey personality (playful colour, chunky rounded controls, card-table motifs, celebratory moments) rather than the corporate dashboard look. The **WCAG 2.1 AA accessibility floor still applies in full** — fun must never cost across-table legibility, which is the whole point of the app.

- **Two user-toggleable themes on one shared, tokenized theme layer** (same layout and components; only the skin swaps): **A — "Felt & Chips"** (card-table felt, brass, ivory score chips) and **B — "Party Arcade"** (bright, loud, chunky, confetti). The toggle is a **persisted per-device preference**. Both themes are held to AA contrast *and* across-table legibility — B is held to the same legibility bar despite being louder.
- **Two views, switched by activity:**
  - **Circle view — for VIEWING during the game.** The phone lies flat on the table; players are arranged around a ring with each player's score oriented to face their own seat; the scorekeeper's seat sits upright at the bottom. Readable from all sides.
  - **Table / list view — for ENTERING scores.** Scorekeeper-facing and upright, with the custom on-screen number pad and the confirm-round step.
- **Static seating order in both views.** Neither view ever reorders players by score; seating is the stable anchor at the table, and the leader is only *indicated* (crown/highlight), never repositioned.

The full design proposal — themes, layouts, and rationale — is in `docs/ui-direction.md`.

## Key Architecture Decisions

- **Pure client-side, no backend, no database** — one scorekeeper, one device, often offline. A server would add hosting, latency, and an offline failure mode while buying nothing for v1. Trade-off: diverges from Roger's usual Next.js + Prisma stack, but re-platforming a small app later is cheap. (Decision 2026-06-02.)
- **Local-storage persistence** — current game only; no cross-game data, consistent with stats being deferred.
- **Single-page app** — setup → play → end-game, all client-rendered.

## Technology Stack

- **React + Vite** — lightweight SPA, fast dev, simple PWA story. (To be confirmed at build time; chosen over Next.js because there is no server-side need.)
- **PWA** (service worker + manifest) for offline use and home-screen install.
- **localStorage** for persistence.
- Dev server must run with `--host` (Roger's WSL2 → Windows browser setup).

## Security Considerations

- No accounts, no personal data beyond freely-typed player names, no network calls — minimal attack surface.
- All data stays on the device in local storage; nothing transmitted.

## Performance Requirements

- Trivial load: a handful of players, dozens-to-hundreds of rounds at most. No performance concerns; target is instant interaction and sub-second cold start.

## Dependencies & Risks

- Minimal third-party dependencies (React, Vite, the PWA plugin — now wired). Keep the tree small. Two dev-only test dependencies were added in the Phase 3 hardening (jsdom and @testing-library/react) so the real app shell can be mounted in a browser-like test; neither ships in the production app. The PWA icon generation adds **no** dependency — it's a hand-rolled zero-dep Node script (`scripts/generate-icons.mjs`, run only when regenerating placeholder art). The two self-hosted display fonts (Nunito + Baloo 2, Open Font License) are bundled assets in `public/fonts/`, not npm packages.
- Main risk is **scoring-rule correctness**, not infrastructure — the engine must be thoroughly unit-tested against the rules and edge cases (Assaf ties, multiple catchers, 100-halving, elimination).
- **Known dev-toolchain advisory (flagged 2026-06-02, not shipped):** `npm audit` reports vulnerabilities in the Vite/Vitest/esbuild dev chain (one rated critical, in the Vitest UI server). These affect only the local development and test tooling, never the built PWA, and are unrelated to the dependencies added in Phase 3. Recommend addressing during a tooling-upgrade pass before any public deploy; not a blocker for current build phases. **Re-checked 2026-07-29 at v1.1:** the count has grown to **9 advisories, one of them critical**, still all in the build-and-test tooling. A production-only audit, covering just what a player installs, reports **zero**. Deferred by Roger's decision, and deliberately not bundled with the v1.1 app release, because a toolchain upgrade changes the offline service worker and the file fingerprints that carry a new version onto an installed phone. ## Resolved Decisions

*Entries are from 2026-06-02 unless a different date is given.*

- **A player who leaves keeps their row, their score and their history (2026-09-03, v1.2)** — removing a player takes them out of the play, not out of the record. Their row stays on the scoresheet and in the final standings, marked as having left, and the rounds they played before leaving stay intact and valid. *Why:* the scoresheet is the digital twin of the paper sheet, and on paper nobody erases a column because its owner went home. Deleting the row would also mean rewriting rounds that genuinely happened, which is precisely what the recompute-from-history guarantee exists to prevent.
- **A player who has left is shown, but is skipped when the app picks the winner and the live leader (2026-09-03, v1.2)** — exactly the treatment a knocked-out player already gets. *Why, in Roger's words:* a player leaving while on a score of 124 cannot be the winner if the game continues for another hour and the other players reach 300 and beyond. Winning belongs to the people who played to the end. Reusing the knocked-out player's treatment also means the app has one rule for "shown but not in contention" rather than two.
- **The removal control is a minus button on the player's row inside "Rearrange seats" (2026-09-03, v1.2)** — it sits beside the existing up and down move buttons. *Why:* that mode is already where the scorekeeper says who is sitting where, so who is at the table at all belongs in the same place. It also keeps a destructive control off the Play screen, where the frequently-pressed buttons live and a phone is lying flat on a busy table.
- **Removal applies immediately, deliberately outside that screen's "nothing commits until Save order" model (2026-09-03, v1.2)** — it carries its own confirmation instead. *Why:* seat order is a display preference, so it can sensibly be shuffled around and then abandoned. A player leaving is a fact about the game that changes the standings, and holding it as a pending edit alongside reorder moves would leave the scorekeeper asking "did that actually save?" about something that matters. **This is recorded because it knowingly breaks that screen's own model**, and a future reader would otherwise take it for an oversight and "fix" it.
- **Removal cannot be undone (2026-09-03, v1.2)** — there is no reversing step. *Why:* it cannot happen by accident, because it takes three deliberate acts, entering Seats mode, choosing remove, and then confirming. Getting somebody back is done through "Add Player", which re-seeds them like any other mid-game joiner rather than pretending they never left.
- **When a departure leaves one active player, the game ends automatically, whether or not an elimination score is set (2026-09-03, v1.2)** — *Why:* that is what has actually happened when everybody else has gone home, and one player cannot play a round. **Note that this widens an existing condition:** ending the game on a single survivor today also requires an elimination score to have been set, and after this change a departure ends the game on its own.
- **Consequence, recorded on purpose: the last player at the table is crowned even if somebody who left holds a lower score (2026-09-03, v1.2)** — this follows from the two decisions above, that a player who has left is not in contention and that one remaining player ends the game. *Why write it down:* on the final screen it will look like the wrong winner to anybody who does not know both rules, and it is exactly the kind of thing that gets reported as a bug and then "corrected" later. It is the intended outcome.
- **The keep-screen-on control lives in the header beside the theme toggle, and it is on by default (2026-09-03, v1.2)** — not on the Setup screen with the other settings. *Why:* the reason somebody switches it off is a phone running out of battery in the middle of a game, so the control has to be reachable during the game and not only before it starts. On by default, because holding the screen awake is the whole point of the feature; the off switch is there for the battery.
- **A hold the phone takes back is asked for again after a short wait, not instantly (2026-09-03, v1.2, review pass)** — one second the first time, then two, four and so on up to a minute, starting over whenever the app is reopened or the hold lasts a healthy while. *Why not instantly:* if a phone hands the hold over and takes it straight back, asking again immediately is an unbroken loop that would freeze the app outright — the worst failure this feature could have. Waiting a second costs nothing anybody can see, because a phone's own screen timeout is fifteen to thirty seconds, and it means a phone that keeps refusing is asked once a minute rather than thousands of times a second. **The same retry closed a separate gap for free:** a phone that refused because it was low on battery used to keep the warning up after being plugged in, until the app happened to be closed and reopened. It now clears itself. **The numbers themselves are a judgement call, not a measurement.** One second doubling to a ceiling of a minute is a reasonable shape for the problem, and nothing has been measured that says a different pair of numbers would be worse.
- **The button reports the hold, not the setting, and it has a fifth appearance for the gap between them (2026-09-03, v1.2, review pass)** — a hollow, unlit bulb means "you have this switched on and the phone is not holding it this moment". *Why:* the deliberate one-second wait above creates a real moment where the setting and the reality disagree, and the whole point of the fix is that the button must never claim something is happening when it is not. The border still shows the setting and the bulb shows the reality, so the two are readable at once.
- **On a phone that cannot keep the screen on, tapping the button explains why; on a phone that has refused, tapping it still switches the feature off (2026-09-03, v1.2, review pass)** — deliberately two different behaviours. *Why:* on a phone without the capability the tap previously did nothing at all — the button visibly depressed under the thumb and then nothing happened, no message, no change — so it now opens a short explanation. On a phone that has merely refused, the tap has always had a real job, which is to let a scorekeeper with a dying battery switch the feature off, and taking that away to show a message would have been a worse trade. A screen reader is told about a refusal through a spoken status line instead, which is what the accessibility rule actually asks for. *This deviates from the reviewer's suggestion, which was one dialog for both cases.*
- **The button's state symbols are drawn by the app rather than typed as emoji (2026-09-03, v1.2, review pass)** — *Why:* the two symbols it shipped with, the bulb and the sleep marks, are emoji that every platform draws in its own fixed colours, so the app's instructions about their colour did nothing whatsoever. Four of the contrast figures written down for this control described a colour that never appeared on screen — the "greyed out" state was in fact a full-colour yellow bulb with a grey line through it. Drawing the shapes means the app controls their colour on every phone, in both themes, and it also removes the last thing on this control that depended on a font the phone might not have.
- **In a knocked-out player's row, the final screen's "Yaniv" and "Assaf" words keep the words and lose the colour (2026-09-03, v1.2, review pass)** — *Why:* those rows are dimmed, which drags the small green and red words down to between 2.3 and 3.4 against a requirement of 4.5, and in an elimination game the players who went out are exactly the ones most likely to have an Assaf against them. **No colour can fix it:** measured, the very best any colour could reach through that dimming is 4.27 on one theme and 4.66 on the other, using text this app's palette does not even allow. So in those rows the words are shown in the row's ordinary ink, which reads no worse than the player's own name beside it. Nothing is lost that carries meaning, because each part has always been the outcome word as well as the colour. The underlying dimming fault is pre-existing, ranked down by Roger, and still on the follow-up list. **That arithmetic has not been independently checked**, because the reviewer asked to check it was lost to a server overload, so it is carried as needing confirmation on the follow-up list.
- **Keeping the screen on is a per-phone setting, not part of the game (2026-09-03)** — the preference is stored on its own, exactly like the theme, and deliberately **not** inside the saved game. *Why:* the saved game is the scoresheet, and anything written into it risks the game in progress; a screen preference has nothing to do with a game and outlives any number of them. The saved-game format was **not** version-bumped, so a game already in progress on someone's phone is untouched by this release.
- **The screen is asked for again every time the app comes back to the front (2026-09-03)** — phones silently drop the "keep the screen on" hold the moment the app is backgrounded or the phone is locked, and never give it back on their own. Without asking again the feature would work once per launch and then quietly stop, which nobody would notice until the phone started locking mid-game again. *Why it is called out:* it is the single thing most likely to be got wrong here, and it is covered by a test written so that removing the re-ask makes the test fail.
- **The keep-screen-on control stays icon-only, and the width reason first given for it was wrong (2026-09-03, corrected in the review pass)** — the original entry here said a worded control would have forced the header onto two rows on every phone, and that the top bar's contents already came to about 314px of the 288px a 320px phone gives. **The header was then measured properly during the review, and that is not true.** The top bar is two rows at every phone width from 320px up to about 430px whichever control it carries, and it returns to one row only around 470px, which is wider than any phone on sale. The icon therefore never avoided a second row. **Roger's call, taken with that correction in front of him, is that the control stays icon-only**, which makes it a free choice rather than a forced one: the header wraps either way, so words would cost the same height and gain little. The cost is that an icon is less self-explanatory than a word, so the control is also explained in Help. *The superseded reasoning is left visible on purpose*, because a future reader who sees an icon and a two-row header should know the icon is not what put the second row there. A separate measurement problem was found alongside it and is on the follow-up list under Current Status: one of the characters used in the app's own button labels is not in either bundled font, so width figures derived from those fonts need checking against what the fonts actually contain.
- **The end-of-game Yaniv count is one combined number (2026-09-03, v1.2)** — each player's count on the final screen adds the calls that were caught in an Assaf to the successful ones and shows a single total, so six successful and two caught reads as eight. *Why:* what players talk about after a game is how often somebody dared to call "Yaniv!", not only how often they got away with it, and splitting the count into two numbers makes a busier screen that answers a question nobody asks out loud. Colour-coding the two parts within the total was wanted rather than required, and as built the split is carried by the outcome words as well as the colour, so the colour is never the only thing saying which part is which.
- **"Most successful Yaniv! calls" stays successful-only, and the label now says so (2026-09-03, v1.2)** — the table column shows the combined count, but the single stat line under the table deliberately still counts only the calls that came off. *Why:* the line reads as an achievement, being the player who called it and got away with it most often, and folding in the calls that were caught would let it be won by whoever gambled most recklessly. The column counts attempts; the line counts wins. The word "successful" was added to the label so the two different numbers on the same screen cannot be mistaken for the same measure. **Roger has agreed to this call (2026-09-03)**, and it is worth knowing that switching the line to the combined total would be a one-word change in two places if he ever changes his mind.
- **The Assaf count is derived from the round history, never stored (2026-09-03, v1.2)** — the new per-player count of "called Yaniv! and got caught" is worked out by replaying the rounds, exactly like every cumulative total, and is not written into the saved game. *Why:* it is the engine's locked design principle, and it is what keeps the number right after an undo or a correction instead of leaving a stale figure on screen. The saved-game format was **not** version-bumped, so games in progress on already-installed phones are untouched by this change.
- **The stars beside the old Yaniv count were dropped, and that was a width decision (2026-09-03, v1.2)** — the column used to draw one star per successful call. *Why they went:* a combined total is by definition a bigger number, and a run of eight stars plus a two-part split does not fit the column on a 320px phone, where the four columns share about 208px of content width. The outcome words carry more than the stars did, since a star could never distinguish a success from an Assaf. **Roger has agreed to this call (2026-09-03).**
- **The end screen's "Yaniv!" column header stays as it is, and the clash with the line beneath it is known and accepted (2026-09-03, v1.2, review pass)** — the column now counts every call a player made, while the single stat line under the table reads "Most successful Yaniv! calls" and counts only the ones that came off. Twiggy recommended renaming the column to "Calls", because read across a table both headings read as "Yaniv!" and the two numbers mean different things. Roger accepted the point and declined the change. *Why it is written down:* two numbers on one screen, both labelled "Yaniv!", meaning different things is exactly the sort of thing that gets reported later as a bug and then "fixed" by somebody who does not know it was discussed. It was seen, understood and left.
- **Two of the reviewer's own tests were wrong about timing, and were rewritten rather than deleted or loosened (2026-09-03, v1.2, review pass)** — two tests demanded that the app get the screen hold back within a single tick of the phone taking it away, which contradicted two other tests in the same set asserting, at that same instant, that no hold is held. No code can satisfy both. *The ruling:* the intent of the two tests was right and their timing was wrong, so they were rewritten to drive the clock forward to the point where recovery is actually due, and then checked by mutation to confirm they still catch the fault they were written for. *Why this is recorded:* the easy way out was to delete them or soften them until they passed, which leaves a green suite and an unguarded fault, and this project has already been bitten by two safeguards that turned out to be decorative. **This is also what closes the two deliberately-failing tests that stood earlier in the day: the suite is now fully green.**
- **The dimmed eliminated-player text is no longer a high priority (2026-09-03)** — the measured contrast failure on a knocked-out player's score and on the ring's "OUT" marker had been top of the follow-up list since v1.0, and Roger has moved it down. *Why:* most games are played with everybody staying to the end, and the elimination threshold is an optional setting that is rarely used, so the defect is rarely on anybody's screen. **It is ranked lower, not closed and not accepted.** It stays on the follow-up list under Current Status as a real, measured accessibility failure.
- **Multiple-catcher tie-breaking** — confirmed: lowest hand among the catchers starts the next round; ties broken by seating order after the caller.
- **Round editing** — confirmed: most-recent-round-only for v1 (no editing of arbitrary past rounds).
- **Distribution model** — confirmed (Reading A): the app is given to many people who each run their own **independent** game on their own device, concurrently and offline. No shared/synced game across devices (that remains deferred). Delivered as an installable PWA from a static URL; after first install each device is fully self-contained.
- **Halving — no cascade, and no re-trigger while parked** — halving fires at most once per player per round. A total landing on 200 halves to 100 and stops (it does **not** continue to 50), even though 100 is itself a multiple of 100. **And it must not resume on a later round:** a player left sitting on an exact 100/200/300 by that halving is halved again only if a subsequent round *moves* them onto an exact hundred. Scoring 0 — which is exactly what a successful Yaniv caller scores — leaves them where they are. *Roger hit this in a real game on 2026-09-09: he reached 200, was correctly halved to 100, then called a successful Yaniv and was halved again to 50. The rule as written above had said only "new total is a multiple of 100", which is why the engine did it.*
- **Halving vs. elimination order** — halving is applied **before** the elimination check. If an (optional) elimination score is itself a round multiple of 100 and a player lands on it exactly, the halving triggers first and rescues the player from being knocked out that round.
- **Elimination boundary** — a player is eliminated only when their cumulative total is **strictly greater than** the elimination score, never when equal to it.
- **Undo/edit = replay from history** — the round-history list is the single source of truth; cumulative totals, halving callouts, eliminations, who-starts-next, and the per-player successful-Yaniv count are all derived by recomputing from history, never by patching deltas in place.
- **Standings in static seating order (no score sort)** — standings are shown in the fixed order players sit around the table and are **never reordered by score**. The leader is only indicated (crown/highlight), not repositioned. *Why:* seating is the stable physical anchor; reordering would make the on-table scoreboard confusing to read at a glance. (Corrects the earlier "sorted lowest-first" spec; the engine already returns standings in seat order, so this is a display/spec correction only.)
- **Mid-game join** — a player may join an in-progress game, seeded at the highest cumulative among still-active players; no halving on the seed; normal play (incl. future 100-halving) thereafter; never instantly eliminated; takes the next seat (the ring grows); recorded as a replayable history event with the seed derived (never stored). *Why:* lets a latecomer join a live table fairly without a head start, while preserving the recompute-from-history guarantee. (Full rules in Scoring Engine.)
- **Two themes on one tokenized layer (A + B)** — two user-toggleable skins, "Felt & Chips" (A) and "Party Arcade" (B), on a single shared theme layer; toggle is a persisted per-device preference; both held to WCAG AA contrast and across-table legibility. *Why:* gives the app personality and player choice without forking the layout or compromising legibility.
- **Two-view model (circle = view / table = entry)** — a circle view for viewing during play (phone flat, scores oriented to each seat) and a table/list view for entering scores (number pad + confirm-round step); both in static seating order. *Why:* the resting scoreboard must read from all sides of the table, while fast entry needs a single upright orientation — different jobs, different views.
- **Circle ring is seat-fixed; rank is indicated, not reordered (Twiggy's recommendation, adopted)** — the ring stays in fixed seating order so each player's chip stays in their physical direction (rotation is only meaningful that way); the leader is shown with a crown and the big-board list is the escape hatch for tight tables. The circle never physically reorders by score. *Why:* honours "static seating order" and keeps the signature per-seat orientation; the upright big-board `<table>` simultaneously satisfies the WCAG semantic-standings requirement.
- **Landing page + in-app Help, sharing single-source copy** — the app ships with a public landing page (on the same static URL it's distributed from) carrying the "why install", Android and iPhone/iPad install steps, and both how-to bodies; and an in-app Help screen carrying the same two bodies. The copy is written **once** per body and reused in both places. *Why:* the audience is non-technical casual players who need install hand-holding (and iPhone users specifically must be told to use Safari, since other browsers can't install a PWA on iOS), and the in-app copy means a player can re-check things mid-game with no signal. Single-source copy prevents the landing page and the app from disagreeing. Drafted copy lives in `docs/landing-and-help-content.md`. Consistent with the URL/PWA distribution model — the landing page *is* the install entry point each device uses. (Decision 2026-06-02.)
- **"How to Use" and "How to Play" are two separate bodies of copy** — the help content is split into two independently-titled guides: **How to Use** (operating the scorekeeper — set up, enter a round, read standings + who-starts-next, undo, add a player mid-game, end game + the per-game successful-Yaniv stat, switch themes) and **How to Play** (the rules of Yaniv itself, drawn from `YanivGameRules.txt` — object, card values, a turn, calling Yaniv, Successful Yaniv vs. Assaf with the +30 and a worked example, winning, and the common house rules). Both surfaces (landing page and in-app Help) show **both** bodies, clearly distinguished; the in-app Help uses two labelled tabs/sections. *Why:* Roger clarified the original draft was really "how to use the app" and that the game's rules are a separate thing — a seasoned player only needs How to Use, while a newcomer needs How to Play. Mixing them muddied both. Keeping them apart (and never mixing rules-teaching into the app-operation copy, or app buttons into the rules copy) keeps each scannable for its reader. (Decision 2026-06-02.)
- **Store contract extended for mid-game join (Turing, UI build)** — the state store gained `addPlayer(name)` (mid-game join: builds a Player with a name-independent id, the next seat, and the join marker; the engine derives the seed) and `removePlayer(id)` (recovers from an edit/undo that strands a joiner), plus a derived `engineError` exposed alongside `game`. *Why:* the engine already supports joins via `Player.joinsBeforeRoundIndex`, but the store had no way to grow the player set after `startGame`; this is the minimal extension to wire the brief's mid-game-join and error-handling requirements. The pure engine and persistence layers were NOT changed.

- **End game asks for confirmation (2026-07-29, v1.1):** tapping "End game" on the Play screen now takes a confirmation step before the game actually ends. *Why:* this is the only action in the app that cannot be recovered. Undo reverses the most recent round, and it does not cover the end-game step, so a single mis-tap on a phone lying flat on a crowded table ended a live game with no way back to it. A confirmation step is the cheapest possible guard against losing a game that people are still playing.

- **Reordering the seating is display-only, and only in the circle view (2026-07-29, v1.1):** the scorekeeper can rearrange the ring in the circular "players around the table" view so it matches where people are actually sitting after a mid-game seat swap. This is deliberately scoped as a viewing preference and nothing more, and the scoring engine's seat order is not changed. **What deliberately keeps the original seat order:** who starts the next round; the tie-break when an Assaf has several catchers (both of these rank by seat order); the round-history model and the recompute-from-history guarantee; and the column order of the vertical scoresheet (Big Board). *Why:* the problem being solved is that the picture on screen should match the picture in the room, which is a display concern. Making seat order genuinely mutable would reach into the scoring rules, and rearranging the ring could then retroactively change what happened in a past round, which must never be possible. The scoresheet is the paper record, and stable columns for the whole game are the correct behaviour for a scoresheet, exactly as on a handwritten sheet. The rearrangement is stored with the game as a per-game display preference, so a refresh does not lose it. **A future reader should not assume seating order was made changeable everywhere. It was not, and that narrow scope is what keeps this feature small and safe.**

- **The saved-game format was deliberately NOT version-bumped (2026-07-29, v1.1). This is the most important thing on this page.** The new seating arrangement is stored as an optional extra piece of information, which means a game already in progress on someone's phone opens perfectly normally under v1.1, **and** a game saved by v1.1 opens perfectly normally under v1.0. That makes a rollback safe in both directions, which matters enormously for an app that lives on people's phones and cannot be reached once installed. *Why this must be written down:* bumping that version number would cause every installed phone to throw away the game it currently has open. **Nobody should ever bump it without first writing a migration that carries existing saved games across.** The temptation to bump it "for tidiness" is real, and the cost is a room full of people losing a live game.

- **The "New game" confirmation is deliberately conditional (2026-07-29, v1.1):** it appears only once at least one round has been recorded, and it is never shown in the error-recovery state where that button is the only way out of a stuck screen. *Why:* before any round is recorded, the only things a new game discards are typed-in names and a seating arrangement, and Rematch preserves both of those anyway. A confirmation at that point protects nothing and is pure friction. A confirmation that asks about nothing teaches people to tap straight through confirmations, which weakens the two that genuinely matter.

- **Rearranging seats uses buttons, not drag-and-drop (2026-07-29, v1.1).** Deliberate. *Why:* dragging small chips around a rotated ring on a phone screen is fiddly and error-prone even for someone with steady hands, and it is simply unusable for anyone navigating by keyboard or with a screen reader. Move buttons serve everyone, including the people drag-and-drop would have excluded, and nothing is applied until "Save order" is pressed. This is not a shortcut taken to save effort; it is the better interaction for this specific control.

- **"End" is allowed as a short visible label on the Play screen (2026-07-29, v1.1).** The visible label is just "End", while the full wording is preserved for screen readers so the spoken name of the control is never merely "End". *Why:* the confirmation step is the safeguard against a mis-tap, so the label no longer has to carry that job on its own, and the two saved rows of screen space are worth real money on a phone lying flat on a table. **This was Roger's call and it reverses an earlier reviewer recommendation to keep the two controls further apart, so the reasoning is recorded here deliberately.** Without it, someone will eventually "fix" this back and quietly undo a decision that was made with the trade-off in full view.

- **The circle's centre button reads "New Round", with no symbol in front of it, on both views (2026-07-29, v1.1).** Roger asked for the change on the circle view. It was applied to the vertical scoresheet view as well, so the same action never reads differently depending on which view you happen to be looking at. Capital R on "Round" in both places. *Why the symbol was dropped rather than kept:* that character is **not present in either of the app's two bundled fonts**, so every phone was drawing it from whatever it happened to have installed, which made its width unpredictable. This is the most frequently pressed control in the whole app, and a control whose width shifts from phone to phone is the last one you want that to happen on. The same underlying problem still applies to two other button symbols, tracked in the follow-up list under Current Status.

- **A real accessibility fault was found and fixed while making that change (2026-07-29, v1.1).** The label sits on two lines, and because of how it was written the button's name was being read out to screen-reader users as a single run-together word, "NewRound". That was wrong from v1.0 onward, not something v1.1 introduced. It is fixed with an explicit space, and it is **pinned by a test**. *Why the test matters more than usual here:* the fault is completely invisible on screen, so there is nothing to notice if it comes back. It is exactly the kind of thing a future tidy-up quietly removes on the grounds that it looks redundant.

- **Publishing to production from a command line is now switched off (2026-07-29).** The hosting platform's guardrail is on, with Roger's explicit approval. Production is now reachable **only** through GitHub. *Why:* a single mistyped command could previously put an unreviewed build in front of every player, and there is no reason anyone should need that route. Everything real goes through the branch and the merge, which is where the review happens anyway.

- **A rollback means reversing the change on `main`, not pressing the instant "republish the previous version" button (2026-07-29).** Two reasons, and the second is the important one. First, whether that instant button still works now that command-line publishing is switched off could not be established without publishing something to production to find out, which is not an acceptable way to test a safety net. Second, and more seriously, republishing only moves the pointer at which version people are served. The unwanted code stays sitting on `main`, ready to go live again on the very next push, most likely at a moment when nobody remembers why it was pulled. Reversing it on `main` removes it properly. **The agreed threshold:** anything wrong with the scores, the scoresheet, or the app failing to open gets reversed immediately, no discussion. Anything cosmetic waits and gets fixed in a follow-up release.

- **The Play screen's buttons stay at 50px, and that is a decision, not an oversight (2026-07-29, v1.1).** The project's own preference is 56px. Raising them was put to Roger and **he did not approve it** for this release, so they shipped at 50px and the item stays on the follow-up list under Current Status. *Why record a change that did not happen:* because otherwise a future reader sees 50px in shipped code, sees 56px in the project's stated preference, and concludes the gap was simply missed. It was seen, raised, and consciously left. They clear the accessibility requirement either way.

- **v1.1 was published in the late afternoon rather than the evening, reversing the earlier recommendation (2026-07-29).** *Why:* the only real risk being managed with release timing is reloading the app underneath somebody who is in the middle of a game. The evening is precisely when people sit down to play cards. Recommending the evening was optimising for the quiet hours of a website, which this is not; the quiet window for this app is earlier in the day. The earlier reasoning was simply pointed at the wrong thing.

- **A Content-Security-Policy was deliberately not bundled with this release (2026-07-29).** It is planned as its own separate change, with its own preview and its own human look. *Why:* getting one of these even slightly wrong does not produce an error message anyone can read, it produces a blank screen, on an app that people run offline on their phones and that cannot be reached to be fixed once installed. It also has no test coverage in this project, so nothing would have caught a mistake before players did. Bundling it with four user-facing features would also have meant that if anything went wrong, there would be no way to tell which change caused it.

### Process lessons from the v1.1 build (2026-07-29)

Worth carrying into the next build, not filed away.

- **Two safeguards in the test suite turned out to be decorative.** The code each was supposed to be protecting could be deleted outright and the test still passed, so neither was guarding anything. Both were caught by deliberately breaking a line of the app to check that something actually fails, which is the only reliable way to tell a real safeguard from a comfortable-looking one. Worth doing again on anything genuinely important.
- **A reviewer's test file should be committed before anyone edits it.** In this build a test file was added and then rewritten inside a single commit, which makes the rewrite impossible to inspect: the record shows the finished version but not what was changed or why. Commit the reviewer's version first, then change it in a second step.

### Build-time recommendations adopted (from team plan review, 2026-06-02)

- **Round entry uses a custom fixed on-screen number pad**, not the native keyboard (speed of the repeated entry loop is the core value).
- **A "confirm round" review step** is shown before each round commits (errors are common; undo is most-recent-only).
- **Hosting on Netlify**; PWA built with `vite-plugin-pwa` using an auto-update strategy to avoid the stale-service-worker trap; full app shell precached (self-hosted fonts) for reliable offline.
- **Accessibility target: WCAG 2.1 AA.**
- **Scoring engine + full unit-test suite built first**, before any UI — v1 correctness is the only defence for offline devices that can't be patched.
